# SqlParserX 模块依赖与包引用结构设计

## 1. 设计目标

SqlParserX 使用 `sqlparserx-engine` 聚合管理解析内核，并将原 `sqlparserx-core` 中混合的 SQL 语法解析职责拆分为两个独立 Jar Module：

| Module | 架构定位 | 核心职责 |
|---|---|---|
| `sqlparserx-engine` | 解析引擎聚合父模块 | 使用 `packaging=pom` 聚合 Syntax/Core，统一管理 Java 版本、Druid 版本和解析引擎测试依赖；不包含 Java 业务代码 |
| `sqlparserx-syntax` | SQL 语法解析层 | 统一维护 Druid 版本、SQL→AST、多语句解析、SQL 切分，以及后续数据源 Lexer、StatementParser、AST Node 扩展 |
| `sqlparserx-core` | SQL 业务解析层 | 基于语法层输出的 Druid AST，实现真实表、建表结构、表/字段血缘、函数和 SQL 权限改写 |

两层使用 `DbType + SQLStatement AST` 作为连接契约。项目不额外复制一套 AST，避免 Druid AST 与自有 AST 之间长期转换和同步。

## 2. Maven Module 依赖结构

工程目录与聚合关系：

```text
SqlParserX（根 Reactor）
├── sqlparserx-engine（聚合父模块，packaging=pom）
│   ├── sqlparserx-syntax（jar）
│   └── sqlparserx-core（jar，依赖 syntax）
├── sqlparserx-web（jar）
├── sqlparserx-mcp-server-sse（独立构建）
└── sqlparserx-ui
```

```text
                         ┌─────────────────────┐
                         │    sqlparserx-ui    │
                         └──────────┬──────────┘
                                    │ HTTP
                                    ▼
┌──────────────────────┐   ┌─────────────────────┐
│ sqlparserx-mcp-      │   │   sqlparserx-web    │
│ server-sse           │   └──────────┬──────────┘
└──────────┬───────────┘              │
           ├──────────────┬────────────┘
           │              ▼
           │      ┌─────────────────────┐
           │      │   sqlparserx-core   │
           │      │   SQL 业务解析层     │
           │      └──────────┬──────────┘
           │                 │
           └─────────────────┼──────────────────┐
                             ▼                  │
                    ┌─────────────────────┐      │
                    │ sqlparserx-syntax   │◀─────┘
                    │ SQL 语法解析层       │  出口模块直接使用语法 API 时显式依赖
                    └──────────┬──────────┘
                               ▼
                    ┌─────────────────────┐
                    │ Druid 1.2.28        │
                    │ commons-lang3       │
                    └─────────────────────┘
```

Maven Reactor 构建顺序：

```text
SqlParserX → sqlparserx-engine → sqlparserx-syntax → sqlparserx-core → sqlparserx-web
```

`sqlparserx-mcp-server-sse` 当前保持独立构建，但依赖关系同样是 Core + Syntax。

## 3. Module 依赖规则

| 调用方 | 允许依赖 | 原因 |
|---|---|---|
| 根 `SqlParserX` | 聚合 `sqlparserx-engine`、`sqlparserx-web` | 管理整个仓库的 Reactor 与通用构建插件 |
| `sqlparserx-engine` | 父 `SqlParserX`；聚合 Syntax/Core | 管理解析引擎公共版本和依赖，不产生 Jar |
| `sqlparserx-syntax` | Druid、commons-lang3 | 语法层拥有 Druid 版本和 Parser 入口 |
| `sqlparserx-core` | `sqlparserx-syntax` | 业务层通过 Syntax 将 SQL 转换为 AST，再进行业务分析 |
| `sqlparserx-web` | `sqlparserx-core`；直接使用语法校验、`DbType` 时显式依赖 `sqlparserx-syntax` | Web 只负责编排和协议转换，不实现解析算法 |
| `sqlparserx-mcp-server-sse` | `sqlparserx-core`；直接使用 `DbType` 时显式依赖 `sqlparserx-syntax` | MCP 只暴露 Core/Syntax 已有能力 |
| `sqlparserx-ui` | Web HTTP API | 前端不直接依赖 Java Module |

禁止的依赖方向：

```text
sqlparserx-syntax -X-> sqlparserx-core
sqlparserx-core   -X-> sqlparserx-web / sqlparserx-mcp-server-sse
Druid             -X-> 任意 SqlParserX 业务模型
```

## 4. `sqlparserx-syntax` 包结构

```text
sqlparserx-engine
└── sqlparserx-syntax
    └── src/main/java/com/dtstack/sqlparserx/syntax
        ├── SqlSyntaxParser.java
        ├── SqlSyntaxParserFactory.java
        └── druid
            └── DruidSqlSyntaxParser.java
```

| 包 / 类型 | 职责 |
|---|---|
| `SqlSyntaxParser` | 对外提供单条解析、多条解析和 SQL 切分的统一语法契约 |
| `SqlSyntaxParserFactory` | 根据 `DbType` 创建语法解析器；后续作为方言 Parser 注册入口 |
| `syntax.druid.DruidSqlSyntaxParser` | 基于 Druid `SQLParserUtils`、Lexer 和 StatementParser 的默认实现 |
| `syntax.dialect.<db>`（后续） | 放置 SqlParserX 自维护的数据源语法扩展，不放业务血缘或表解析逻辑 |

当前统一语法 API：

```java
SqlSyntaxParser parser = SqlSyntaxParserFactory.getParser(DbType.doris);

SQLStatement statement = parser.parseStatement(sql);
List<SQLStatement> statements = parser.parseStatements(sqlScript);
List<String> originalSqlList = parser.split(sqlScript);
```

语法层允许出现的代码：

- `DbType` 方言选择与注册。
- SQL Lexer、StatementParser、AST Node 和 Visitor 基础设施。
- SQL 文本到 `SQLStatement` 的转换。
- 多语句解析、语法校验和切分。
- 数据源语法兼容测试。

语法层禁止出现的代码：

- 主表、真实表和建表业务模型解析。
- 表血缘、字段血缘推导。
- 行级或列级权限业务规则。
- Web DTO、MCP Tool 或子产品任务模型。

## 5. `sqlparserx-core` 包结构

```text
sqlparserx-engine
└── sqlparserx-core
    └── src/main/java/com/dtstack/sqlparserx/core
        ├── parser
        │   ├── ISqlParser.java
        │   ├── SqlParserFactory.java
        │   ├── base
        │   │   ├── BaseSqlParser.java
        │   │   ├── table
        │   │   ├── lineage
        │   │   ├── sqlfilter
        │   │   └── parameter
        │   └── <dialect>
        │       ├── mysql
        │       ├── doris
        │       ├── starrocks
        │       └── ...
        ├── select
        ├── domain
        ├── enums
        └── utils
```

Core 可以遍历和修改 Druid AST，因为 AST 是两层公开契约；但 Core 不应再直接调用 `SQLParserUtils.createSQLStatementParser` 或自行实例化 StatementParser。所有 SQL→AST 操作必须经过 `SqlSyntaxParser`。

```java
// 正确：业务层通过 Syntax 获得 AST
SQLStatement statement = SqlSyntaxParserFactory
        .getParser(dbType)
        .parseStatement(sql);

// 禁止：业务层绕过 Syntax 直接创建 Druid Parser
SQLParserUtils.createSQLStatementParser(sql, dbType);
```

## 6. 两层方言包对应关系

同一数据源可以分别拥有语法扩展和业务扩展，两者按数据源名称保持对应：

```text
sqlparserx-syntax
└── syntax/dialect/doris
    ├── DorisLexerExtension
    ├── DorisStatementParserExtension
    └── DorisAstExtension

sqlparserx-core
└── core/parser/doris
    ├── DorisSqlParser
    ├── DorisParseTableClient
    └── DorisParseCreateTableClient
```

| 问题表现 | 修改 Module | 示例 |
|---|---|---|
| SQL 无法解析、关键字不识别 | `sqlparserx-syntax` | Lexer 或 StatementParser 扩展 |
| AST 节点或方言属性缺失 | `sqlparserx-syntax` | 新增或完善方言 AST Node |
| AST 正确但真实表结果错误 | `sqlparserx-core` | 扩展 `IParseTableClient` |
| AST 正确但建表结构缺失 | `sqlparserx-core` | 扩展 `ParseCreateTableClient` |
| AST 正确但血缘结果错误 | `sqlparserx-core` | 扩展血缘 Client 或解析策略 |

## 7. Druid 依赖管理原则

| 原则 | 说明 |
|---|---|
| 版本唯一 | Druid 版本在 `sqlparserx-engine/pom.xml` 的 `dependencyManagement` 中统一定义 |
| 声明唯一 | 只有 `sqlparserx-syntax` 直接声明 Druid 和其 optional 运行依赖 |
| AST 可传递 | Syntax 公共 API 返回 Druid AST，因此 Druid 是 Syntax 的公开传递依赖 |
| Parser 入口收口 | Core/Web 不直接创建 Druid StatementParser，统一通过 `SqlSyntaxParser` |
| 升级先语法层 | 升级 Druid 时先运行 Syntax 方言语法测试，再运行 Core 业务解析回归测试 |

## 8. 构建与测试顺序

```bash
# 在 Engine 目录构建并测试两个子模块
mvn -f sqlparserx-engine/pom.xml test

# 从根 Reactor 精确测试 Syntax + Core
mvn -pl sqlparserx-engine/sqlparserx-syntax,sqlparserx-engine/sqlparserx-core -am test -DskipTests=false

# 完整 Reactor 构建
mvn clean package
```

| 测试层次 | 验证内容 |
|---|---|
| Syntax 单元测试 | SQL→AST、多语句解析、SQL 切分和方言语法扩展 |
| Core 通用测试 | 表解析、建表解析、表/字段血缘、函数和权限改写 |
| Core 方言测试 | Doris、MySQL、StarRocks 等数据源业务差异 |
| Web/MCP 测试 | 参数转换、接口协议和结果序列化，不重复测试解析算法 |

## 9. 后续演进约束

1. 新增数据源时，先确认 Syntax 能生成完整 AST，再实现或复用 Core 业务能力。
2. Syntax 的方言支持集合可以大于 Core 的正式业务支持集合。
3. 只有 Syntax 语法通过、Core 业务结果通过且具备回归用例后，才能对外标记为正式支持。
4. 不为隔离 Druid 而复制自有 AST；除非未来存在第二套长期共存的语法引擎。
5. 新增 Parser、Lexer 或 AST 扩展只能进入 `sqlparserx-syntax`，新增血缘和业务解释逻辑只能进入 `sqlparserx-core`。
