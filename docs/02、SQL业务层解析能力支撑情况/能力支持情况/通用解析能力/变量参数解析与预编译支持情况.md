# 通用解析能力 · 变量参数解析与预编译支持情况

> 维护范围：`sqlparserx-core` 中基于 `BaseSqlParser` / `IParseParameterClient`（`BaseParseParameterClient`）的**变量参数解析与预编译改写能力**。
> Core 入口：`ISqlParser.parseParameterSql` / `ISqlParser.buildSqlByPrepareCompile`。
> 上层汇总入口见 [SQL解析能力&数据源支撑适配情况.md](../datasource/SQL解析能力&数据源支撑适配情况.md)。

## 用例示范（快速上手）

```java
// 1. 获取解析器
ISqlParser sqlParser = SqlParserFactory.getSqlParser(SqlParserDataSourceType.MYSQL);

// 2. 准备带 ${变量} 的 SQL
String sql = "SELECT id, name FROM user_info "
        + "WHERE tenant_id = ${tenantId} AND status = ${status}";

// 3. 配置期：解析变量与输出字段
Map<String, List<DataTypeColumn>> tableColumnsMap = new HashMap<>();
tableColumnsMap.put("user_info", Arrays.asList(
        new DataTypeColumn("tenant_id", "BIGINT", "租户ID"),
        new DataTypeColumn("status", "VARCHAR", "状态")));

ParseParameterResult parseResult = sqlParser.parseParameterSql(sql, true, tableColumnsMap);
System.out.println(parseResult.getInputParams());   // 入参定义：tenantId / status（绑定字段、操作符、是否必填）
System.out.println(parseResult.getOutputParams());  // 出参定义：id / name

// 4. 运行期：预编译改写
Map<String, Object> inParams = new HashMap<>();
inParams.put("tenantId", 1001L);
inParams.put("status", "OPEN");

PrepareCompileResult compileResult = sqlParser.buildSqlByPrepareCompile(sql, inParams, new HashMap<>());
System.out.println(compileResult.getBeautifulSql()); // SELECT ... WHERE tenant_id = ? AND status = ?
System.out.println(compileResult.getInputFields());  // [1001, OPEN]
```

> 当前 `BaseParseParameterClient` 为预留实现（返回 `null`），以上为接口用法示范，待基于 Druid 的具体实现落地后生效。

## 一、能力定位：SQL 转 API 的两个关键时刻

这套能力服务的是「**SQL 转 API / 数据 API**」场景：用户在平台上**手写一条 SQL**，把需要外部传入的值写成 `${变量}` 占位符；平台据此生成一个标准 API，调用方按标准入参传值即可拿到查询结果。

```text
配置期：SQL 里的 ${变量}  ->  解析成 API 入参配置（变量名/绑定字段/操作符/是否必填）
运行期：调用方传入参数值   ->  ${变量} 改写成 ? 并按序绑定执行  ->  返回标准结果
```

- **手写 SQL + 占位符**：SQL 由用户手写，动态值用 `${变量}` 声明，例如 `WHERE tenant_id = ${tenantId}`。
- **标准化入参**：配置期解析出的 `inputParams` 落成 API 入参（`ParamInfo`），调用方只需按名字传值，不必关心 SQL 细节。
- **参数化执行**：运行期把 `${变量}` 改写成 JDBC `?` 并给出有序参数，避免字符串拼接与 SQL 注入；`IN` 集合展开、`LIMIT` 分页上限也由插件统一处理。
- **标准结果**：`SELECT` 字段被解析为输出参数，执行结果按 API 约定返回。

在这条链路上，**SQLParser 只负责「解析」与「改写」两件事**，不连数据库、不执行 SQL、不查元数据：

| 阶段 | SQLParser 要做的事 | 目的 |
|---|---|---|
| 配置期 | 从 SQL 中识别 `${变量}`、所在条件、绑定字段、操作符、必填性，以及 `SELECT` 输出字段 | 产出可落库的 API 入参/出参定义 |
| 运行期 | 依据 AST 中变量位置，把 `${变量}` 按位置改写成 `?`，并按 `?` 顺序产出绑定参数 | 产出可直接交给 JDBC `PreparedStatement` 执行的预编译 SQL 与有序参数 |

## 二、Core 入口与两个核心方法

原实现用一个 `parseApiSql(..., prepareCompile)` 开关在同一个方法里切换两种模式；SqlParserX 将其**拆分为两个语义清晰的核心方法**，分别对应配置期与运行期。

| 阶段 | 核心方法 | 输入 | 输出 | 当前状态 |
|---|---|---|---|---|
| 配置期 | `parseParameterSql` | `stmt`、`isIgnoreSyntaxCheck`、`tableColumnsMap` | `ParseParameterResult` | 预留 ❌ |
| 运行期 | `buildSqlByPrepareCompile` | `stmt`、`inParams`、`columns` | `PrepareCompileResult` | 预留 ❌ |

入口签名：

```java
// 配置期：解析带变量的 SQL（非预编译）
ParseParameterResult parseParameterSql(
        SQLStatement stmt,
        Boolean isIgnoreSyntaxCheck,
        Map<String, List<DataTypeColumn>> tableColumnsMap);

// 运行期：生成预编译 SQL
PrepareCompileResult buildSqlByPrepareCompile(
        SQLStatement stmt,
        Map<String, Object> inParams,
        Map<String, ParamInfo> columns);
```

调用链：

```text
ISqlParser#parseParameterSql / buildSqlByPrepareCompile   （String 入口，内部先 createStatement）
  -> BaseSqlParser#parseParameterSql / buildSqlByPrepareCompile
  -> IParseParameterClient#parseParameterSql / buildSqlByPrepareCompile
  -> BaseParseParameterClient（通用默认实现，方言可按需重写）
```

`ISqlParser` 同时提供 `String sql` 版本作为对外便捷入口，由 `BaseSqlParser` 统一解析成 `SQLStatement` 后转交 `IParseParameterClient`；业务层只需实现 Client 即可。

与旧接口的对应关系：

| 旧入口 | 新入口 |
|---|---|
| `parseApiSql(..., prepareCompile=false)` | `parseParameterSql(stmt, isIgnoreSyntaxCheck, tableColumnsMap)` |
| `parseApiSql(..., prepareCompile=true)` | `buildSqlByPrepareCompile(stmt, inParams, columns)` |

## 三、配置期：`parseParameterSql` —— 动态变量解析

### 3.1 目的

只分析 SQL、不生成可供 JDBC 执行的 `?` SQL，用于在用户保存/发布 API 时产出入参与出参定义。

### 3.2 解析内容

- `${变量}` 的名称；
- 变量所在的条件或表达式（`sqlPart`）；
- 变量绑定的表字段；
- `=`、`IN`、`LIKE` 等操作符；
- 是否为必填参数块（`mustFlag`）；
- `LIMIT` 是否位于最外层（`isOutLayer`）及常量值（`constValue`）；
- `SELECT` 输出字段（`outputParams`）。

### 3.3 输出：`ParseParameterResult`

```text
ParseParameterResult
├── inputParams     List<ParamInfo>     动态变量参数块（入参定义）
├── outputParams    List<ApiParamSpan>  SELECT 输出字段（出参定义）
└── tables          List<Table>         SQL 涉及的表
```

`ApiParamSpan`（变量参数块 / 输出字段）关键字段：

| 字段 | 说明 |
|---|---|
| `sqlPart` | 参数块对应的 SQL 片段 |
| `params` | 参数块内使用的变量名列表 |
| `bindColumns` | 绑定的表字段及元数据（`DataTypeColumn`） |
| `operator` | 操作符（`=` / `IN` / `NOT IN` / `LIKE` …） |
| `mustFlag` | 是否必填参数块 |
| `isOutLayer` / `isConst` / `constValue` | 最外层 `LIMIT` 判定与常量值 |

`ParamInfo`（入参定义）关键字段：

| 字段 | 说明 |
|---|---|
| `name` | 参数名 |
| `fieldName` | 绑定字段名 |
| `operator` | 操作符 |
| `dataType` | 参数类型 |
| `required` / `imperative` | 是否必填 |
| `desc` | 描述 |
| `defaultValue` / `constant` / `groupId` | 默认值、是否常量、分组 |

### 3.4 示例

输入 SQL：

```sql
SELECT id, name
FROM user_info
WHERE tenant_id = ${tenantId}
  AND status = ${status}
```

输出语义：

```json
{
  "inputParams": [
    {
      "sqlPart": "tenant_id = ${tenantId}",
      "params": ["tenantId"],
      "operator": "=",
      "bindColumns": [{"name": "tenant_id", "type": "BIGINT"}]
    },
    {
      "sqlPart": "status = ${status}",
      "params": ["status"],
      "operator": "=",
      "bindColumns": [{"name": "status", "type": "VARCHAR"}]
    }
  ],
  "outputParams": [
    {"sqlPart": "id"},
    {"sqlPart": "name"}
  ]
}
```

`bindColumns` 的 `type`/`comment` 依赖调用方传入的 `tableColumnsMap`；传空 Map 时仍可识别变量与字段关系，但类型等元数据可能不完整。

## 四、运行期：`buildSqlByPrepareCompile` —— 预编译改写

### 4.1 目的

在变量解析的基础上继续改写，把 SQL 变成可以交给 JDBC `PreparedStatement` 执行的形态，避免直接拼接参数值。

### 4.2 改写内容

- 依据 AST 中变量位置，将 `${变量}` 改写为 `?`；
- 删除没有值的非必填参数条件；
- 将 `IN / NOT IN` 集合值展开为多个 `?`；
- 按 SQL 中 `?` 的先后顺序组织绑定参数；
- 按数据源方言处理 `LIMIT / OFFSET`。

### 4.3 输出：`PrepareCompileResult`

```text
PrepareCompileResult
├── beautifulSql    String         `${变量}` 改写后的 SQL（含 `?`）
└── inputFields     List<Object>   与每个 `?` 一一对应的有序参数
```

必须保持的对应关系：

```text
beautifulSql 中第 N 个 ?  <->  inputFields 中第 N 个参数
```

对于集合参数，一个变量可能展开成多个 `?`，下游按序摊平为实际绑定值序列。

### 4.4 输入

| 参数 | 说明 |
|---|---|
| `inParams` | 调用方本次请求的变量名 → 值 |
| `columns` | 已保存的变量配置（`ParamInfo`：类型、是否必填、操作符等） |

### 4.5 示例

输入 SQL 与请求值 `tenantId=1001`、`status=OPEN`：

```sql
SELECT id, name
FROM user_info
WHERE tenant_id = ${tenantId}
  AND status = ${status}
```

输出语义：

```json
{
  "beautifulSql": "SELECT id, name FROM user_info WHERE tenant_id = ? AND status = ?",
  "inputFields": [1001, "OPEN"]
}
```

`tenant_id = ?` 对应 `inputFields[0]=1001`，`status = ?` 对应 `inputFields[1]="OPEN"`，下游按序 `setParam` 即可。

## 五、两个核心方法如何在业务中搭配使用

作用场景在：sql转api中，我们预先设定好一个sql包含变量参数的，结合真实的元数据表字段，解析出入参定义，落库后发布成api；调用方按标准入参传值，运行期再把sql改写成预编译形式并按顺序绑定参数执行。

两个方法是**同一链路上的两个阶段**，按业务生命周期搭配：

```text
配置阶段（编辑/保存/发布）：parseParameterSql        -> inputParams（声明了哪些变量、绑定哪些字段）
运行阶段（收到请求要执行）：buildSqlByPrepareCompile -> beautifulSql + inputFields（? SQL 和有序参数）
```

完整流程（配置期 → 运行期）：

```text
1. 【配置 SQL】用户在平台上新建 API，手写一条 SQL；需要外部传入的值写成 ${变量}。
2. 【表解析】platform 调 SQLParser 表解析 parseTablesWithDbType(sql)，得到 SQL 涉及的表。
3. 【取真实元数据】按表名到底层数据源查真实字段，组装 tableColumnsMap。
4. 【解析变量/输出】parseParameterSql(stmt, isIgnoreSyntaxCheck, tableColumnsMap)
     - 入参：inputParams —— 有哪些 ${变量}、绑定哪个字段、操作符、是否必填；
     - 出参：outputParams —— SELECT 字段，作为 API 返回值定义。
5. 【落配置并发布】把 inputParams 转成 API 入参定义（ParamInfo）连同 SQL 一起保存、发布。
6. 【调用方请求】外部按标准入参传值，例：tenantId=1001、status=OPEN。
7. 【预编译】buildSqlByPrepareCompile(stmt, inParams, columns)
     - beautifulSql —— ${变量} 已按位置改写成 ?；
     - inputFields —— 与每个 ? 一一对应的绑定值（IN 集合会展开）；
     - 如 SQL 自带最外层 LIMIT 且开启分页，再外包一层临时表。
8. 【执行 JDBC】用 beautifulSql 建 PreparedStatement，按 inputFields 顺序 setParam，执行得到结果集。
9. 【返回结果】按第 4 步的 outputParams 约定，把结果集包装成标准 API 返回值。
```

即：**用户用 `${变量}` 指定可替换参数 → 配置期解析出标准入参/出参 → 运行期用请求值生成预编译 SQL 和有序参数 → 直接 JDBC 执行并返回标准结果。**

> 说明：本仓库关注 SQLParser 承担的部分——`${变量}` 的解析与预编译改写；对应配置端在 `dt-center-api`，运行端在 `dt-center-api-server`。

## 六、元数据依赖：`tableColumnsMap`

SQLParser 本身没有数据库连接，也不会主动访问元数据表；如需 `bindColumns` 返回真实字段类型、注释，调用方需先按 SQL 涉及的真实表查出元数据再传入。

```text
原始 SQL
  -> 识别 SQL 涉及的真实表
  -> 上层查询元数据服务/元数据表
  -> 组装 Map<String, List<DataTypeColumn>> tableColumnsMap
  -> parseParameterSql(..., tableColumnsMap)
  -> bindColumns 返回真实 type/comment
```

| 阶段 | 是否需要真实元数据 |
|---|---|
| 配置期 `parseParameterSql` | 需要，用于回填 `bindColumns` 的类型与注释 |
| 运行期 `buildSqlByPrepareCompile` | 不需要，生成 `?` 与排列有序参数只依赖变量位置与顺序 |

> 说明：`DataTypeColumn.type` 保持 `String`，承载的是**数据源方言的原始类型**（如 MySQL `BIGINT`、Hive `array<int>`、Oracle `NUMBER(10,2)`）。SQLParser 只按「表名 + 字段名」匹配元数据后**原样回填**，不对类型做识别或归一化；为兼容不同数据源，这里不使用固定枚举。

## 七、实现思路（基于 Druid）

SqlParserX 统一以 **Druid** 作为 AST 底座：语法层负责把 SQL 解析为 `SQLStatement`，业务层在此基础上完成变量识别与改写。

```text
SQL 文本
  -> Druid 解析（sqlparserx-syntax，构建 SQLStatement AST）
  -> BaseSqlParser 转交 IParseParameterClient
  -> BaseParseParameterClient（基于 Druid AST 遍历）
       识别变量节点 / 条件节点 / 输出字段
       按 SQLUtils 位置信息改写 ${变量} -> ?
       生成 ParseParameterResult / PrepareCompileResult
```

要点：

- **变量识别**：遍历 AST 中的条件、函数、`IN/NOT IN`、`ORDER BY`、`GROUP BY`、`LIMIT` 等节点，定位 `${变量}` 出现位置。
- **等长/坐标安全的改写**：`${name}` 与内部占位形式保持长度一致，或按起止坐标替换并补齐，避免前一次替换导致后续节点坐标偏移。
- **位置还原**：改写后可通过位置信息回填变量所在 SQL 片段（`sqlPart`）。
- **方言适配**：`IN` 集合展开、`LIMIT/OFFSET` 等按数据源方言在对应方言 Client 中覆盖。

## 八、能力边界

| 边界项 | 说明 |
|---|---|
| 变量语法 | 支持 `${name}` 形式，不对带点号的调度变量（如 `${bdp.system.bizdate}`）直接支持 |
| 元数据 | 不连数据库、不查元数据，字段类型/注释依赖调用方传入 `tableColumnsMap` |
| 执行 | 只产出 SQL 与参数，不负责执行与结果包装 |
| 位置信息 | 当前返回 `sqlPart` 语义片段，公共模型未直接暴露 `{start, end}` 字符坐标 |
| 当前实现 | `BaseParseParameterClient` 为预留实现（返回 `null`），方言未落地专项逻辑 |
