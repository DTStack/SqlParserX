# 通用解析能力 · 表血缘解析支持情况

> 维护范围：`sqlparserx-core` 中基于 `BaseSqlParser` / `TableLineageClient` 的**通用表级别血缘解析能力**。
> 实现思路参考：[基于Druid实现表级别血缘解析的核心思路](../../../../reference/sqlparserx核心解析层实现思路/基于Druid实现表级别血缘解析的核心思路.md)。
> 上层汇总入口见 [SQL解析能力&数据源支撑适配情况.md](../datasource/SQL解析能力&数据源支撑适配情况.md)。

## 用例示范（快速上手）

```java
// 1. 获取解析器
ISqlParser sqlParser = SqlParserFactory.getSqlParser(SqlParserDataSourceType.MYSQL);

// 2. 准备写入类 SQL（select 查询不产生表血缘）
String sql = "CREATE TABLE user_order_summary AS "
        + "SELECT u.id, o.amount FROM users u JOIN orders o ON u.id = o.user_id";

// 3. 调用表血缘解析
TableLineageResult result = sqlParser.parseTableLineages(sql);

// 4. 读取结果
List<TableLineage> lineages = result.getTableLineages();
System.out.println(lineages); // users -> user_order_summary；orders -> user_order_summary
```

## 一、实现目标

从 SQL 中推导**来源表 → 目标表**的表级血缘关系。表血缘只认同「有写入」的语句，即 `insert` 与 `create table ... as select`；纯查询 `select` 不产生表血缘。

```text
SQLInsertStatement / SQLCreateTableStatement(AS SELECT)
  → TableLineageClient.parseTableLineages
  → 目标表 + 来源表集合（SelectTableSpecialLineageService 追溯）
  → TableRelation 集合
  → TableLineageResult
```

表血缘与字段血缘共享同一套 `select` 追溯逻辑，二者思路可互相搭配。

## 二、Core 入口与实现位置

| 项目 | 内容 |
|---|---|
| Core 入口 | `ISqlParser.parseTableLineages(String sql)` |
| 默认实现 | `BaseSqlParser.parseTableLineages` → `TableLineageClient` |
| 返回类型 | `TableLineageResult`（目标表 + 来源表集合 + `TableRelation`） |
| 适用语句 | `SQLInsertStatement`、`SQLCreateTableStatement`（AS SELECT） |
| 共享服务 | `SelectTableSpecialLineageService`（from/with as 追溯） |

## 三、支持粒度与深度

### 3.1 SQL 结构场景

| 能力项 | 支持情况 | 说明 |
|---|---|---|
| from 普通表（`SQLExprTableSource`） | **已支持 ✅** | `真实表名 ←→ 表别名` 直接映射 |
| join 场景（`SQLJoinTableSource`） | **已支持 ✅** | 多组 from 合并，如 `table4 t4 left join table5 t5` |
| from 子查询（`SQLSubqueryTableSource`） | **已支持 ✅** | 子查询真实表与别名 `t34` 建立映射 |
| select union 场景 | **已支持 ✅** | 每个 union 分支独立追溯后合并 |
| union all 子查询（`SQLUnionQueryTableSource`） | **已支持 ✅** | 复用 union 查询逻辑 |
| 子查询 + union 结构 | **已支持 ✅** | 复用子查询与 union 逻辑 |
| LATERAL VIEW 表源（`SQLLateralViewTableSource`） | **已支持 ✅** | 复用内部 tableSource 逻辑 |
| `with as` 表映射 | **已支持 ✅** | CTE 别名替换为真实表 |
| `with as insert into/overwrite` | **已支持 ✅** | 主体 select 引用 CTE 别名时替换 |
| 递归 CTE | **已支持 ✅** | 过滤别名自身引用，避免自血缘 |

### 3.2 字段内部场景

| 能力项 | 支持情况 | 说明 |
|---|---|---|
| 字段中嵌套子查询（`SQLQueryExpr`） | **已支持 ✅** | 如 `(select max(col1) from table5 t5) as col2`，可追溯真实表 |

### 3.3 识别深度

| 维度 | 深度 |
|---|---|
| 表识别深度 | `catalog.db.table` ✅ |
| 来源表合并 | 子查询/union 的多个真实表以 `,` 合并，展开为多条来源表 |

## 四、核心流程

1. 取目标表（主表）。
2. 取主体查询的一组来源表，归一为 `真实表名 ↔ 表别名`。
3. 若为 `with as` 结构：构建 `别名 → 一组来源表` 映射，替换主体中引用 CTE 的别名，并补齐未在主查询使用但已定义的 CTE 来源表。
4. 来源表集合与目标表两两组合，生成 `TableRelation`。

## 五、方言策略

| 策略 | 说明 | 启用数据源 |
|---|---|---|
| `CTE_FORWARD_REFERENCE` | CTE 前向引用：允许 CTE 引用后面定义的 CTE | Doris |
| 默认策略 | 不开启上述策略时按标准 CTE 顺序解析 | 其他数据源 |

## 六、能力边界

| 边界项 | 说明 |
|---|---|
| 仅写入语句 | `select` 查询本身不产生表血缘 |
| 只解析一层 | 表血缘为直接来源关系，不做跨语句递归串联 |
| `where ... in` 子查询表 | 属于间接影响/条件依赖，不计入直接表血缘（表解析可识别） |
| CTE 前向引用 | 需数据源显式开启策略，默认不开启 |
